# Device Categories Migration (017-020)

## Overview

This migration set introduces dynamic category management for electronic devices. It replaces the hardcoded category system with a flexible, database-driven approach that allows administrators to create, edit, and delete device categories, and configure category-specific fields.

## Migration Files

### 017_device_categories.sql
Creates the `device_categories` table to store device category definitions.

**Features:**
- Unique category names (case-insensitive)
- Optional description and icon
- Active/inactive status
- Optimistic locking with version field
- Automatic timestamp updates

**Rollback:** `017_device_categories_rollback.sql`

### 018_category_fields.sql
Creates the `category_fields` table to store field configurations for device categories.

**Features:**
- Links fields to categories
- Supports field types: text, number, select, boolean
- Required/optional field configuration
- Custom vs standard field distinction
- Display order for form rendering
- JSON options and validation rules

**Rollback:** `018_category_fields_rollback.sql`

### 019_device_custom_fields.sql
Creates the `device_custom_fields` table to store custom field values for electronic devices.

**Features:**
- Links custom field values to devices
- JSONB storage for flexible data types
- One value per field per device
- Automatic timestamp updates

**Rollback:** `019_device_custom_fields_rollback.sql`

### 020_populate_device_categories.sql
Populates the new tables with existing hardcoded categories and creates default field configurations.

**Actions:**
1. Inserts 6 default categories (Laptops, Tablets, Smartphones, Periféricos, Digitales, Otros)
2. Creates memory_capacity and memory_unit fields for Laptops, Tablets, and Smartphones
3. Adds `category_id` column to `item_types` table
4. Maps existing category strings to new category IDs

**Rollback:** `020_populate_device_categories_rollback.sql`

## How to Apply

### Option 1: Using the apply script (Recommended)

```powershell
# From the project root
node apply-device-categories-migration.js
```

### Option 2: Manual application

Connect to your database and run the migrations in order:

```sql
\i supabase/migrations/017_device_categories.sql
\i supabase/migrations/018_category_fields.sql
\i supabase/migrations/019_device_custom_fields.sql
\i supabase/migrations/020_populate_device_categories.sql
```

### Option 3: Using Supabase CLI

```bash
supabase db push
```

## Verification

After applying the migrations, verify the changes:

```sql
-- Check device_categories table
SELECT * FROM device_categories;

-- Check category_fields table
SELECT * FROM category_fields ORDER BY category_id, display_order;

-- Check item_types now have category_id
SELECT id, name, category, category_id FROM item_types WHERE category IS NOT NULL;

-- Verify indexes
SELECT tablename, indexname FROM pg_indexes 
WHERE tablename IN ('device_categories', 'category_fields', 'device_custom_fields');
```

## Rollback

To rollback all changes, run the rollback scripts in reverse order:

```sql
\i supabase/migrations/020_populate_device_categories_rollback.sql
\i supabase/migrations/019_device_custom_fields_rollback.sql
\i supabase/migrations/018_category_fields_rollback.sql
\i supabase/migrations/017_device_categories_rollback.sql
```

## Impact

### Database Changes
- 3 new tables: `device_categories`, `category_fields`, `device_custom_fields`
- 1 modified table: `item_types` (added `category_id` column)
- Multiple indexes for performance optimization

### Backward Compatibility
- The old `category` column in `item_types` is preserved for backward compatibility
- Existing code will continue to work during the transition period
- The `category` column can be removed in a future migration once all code is updated

### Data Migration
- All existing electronic device categories are migrated to the new system
- Default field configurations are created for memory-related fields
- No data loss occurs during migration

## Notes

- The migration is designed to be idempotent (can be run multiple times safely)
- All foreign key constraints use CASCADE for proper cleanup
- Optimistic locking is implemented via version fields
- All timestamps use `TIMESTAMP WITH TIME ZONE` for proper timezone handling
